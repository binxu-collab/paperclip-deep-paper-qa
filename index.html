Training a Custom Model for Deep Paper QA with Paperclip as an MCP Tool

A small, open-weight model whose only superpower is knowing how to drive a corpus engine well. We distill an agentic teacher into Qwen3-14B with SFT, then sharpen its tool use and answer accuracy with RL — the intelligence lives in the tool, the discipline lives in the policy.

GXL Research June 2026 Qwen3-14B verl + GRPO paperclip MCP

Motivation

State-of-the-art “deep research” over the scientific literature today is done by large frontier models (Claude, GPT, Gemini) driving search/read tools in a loop. It works — but it is expensive (many frontier calls over long contexts per question), closed (you cannot self-host, fine-tune, or run offline), and hard to control (answer style, citation discipline, and stopping behavior are baked into a model you do not own).

The thesis of this project: the hard part of paper QA is not raw model intelligence — it is disciplined tool use over a good corpus. If a model can (a) find the right paper, (b) read exactly the right passages, and (c) stop and answer concisely, then a 14B open model is enough. The intelligence lives in the tool (paperclip, indexing 8M+ papers); the policy we train just has to use it well.

Why MCP?

We expose paperclip as a Model Context Protocol (MCP) server. MCP gives us one clean contract that is identical across three very different consumers — so a trajectory the teacher produced is replayable by the student, and a policy trained in RL behaves identically at eval time. The model only ever sees one tool, paperclip(command=…), and learns to compose shell-like commands against it.

The Tool: Paperclip over MCP

Paperclip is a CLI/HTTP engine over 8M+ full-text papers (bioRxiv, medRxiv, PubMed Central). The agent calls a single MCP tool and passes a shell-like command string:

// the only tool the model ever sees
{
  "name": "paperclip",
  "arguments": {
    "command": "lookup doi 10.1101/2025.11.22.689941",
    "description": "Locate the paper by DOI"
  }
}

Core commands the policy learns to compose:

  • search "<query>" — hybrid BM25 + vector search across the corpus
  • grep "<regex>" /papers/ — sub-second server-side regex over all 8M papers
  • lookup doi <DOI> — resolve a paper and cd into its directory
  • cat / head / sed / scan file "p1" "p2" — targeted reads of content.lines
  • lookup-citation — find every in-text mention of a reference
  • map / sql — fan-out over many papers / structured queries

Each paper is a small read-only filesystem the agent navigates:

/papers/{uuid}/meta.json        # title, authors, doi
/papers/{uuid}/content.lines    # full text with block IDs
/papers/{uuid}/sections/        # sections
/papers/{uuid}/supplements/     # supplementary material

The behavior contract (system prompt, agents/papers/papers_reader.yaml) is deliberately strict: do exactly what was asked, then stop. No over-delivery, no anticipating follow-ups — which makes both the SFT targets and the RL reward well-defined.

1 · Data Collection (Distillation)

We do not hand-write trajectories. A strong teacher (Claude Sonnet 4.6, configured in papers_reader.yaml) answers real evaluation questions while driving paperclip, and we record the full multi-turn conversation.

  • collect_sft_data.py captures the complete trace — system prompt + every tool_call + every tool result + the final answer — rebuilt from the session DB so it is an exact, replayable transcript. --only-passing keeps only correct traces.
  • judge_accuracy.py scores each final answer against ground-truth criteria (e.g. "The solution is: 95%") with Claude → {"pass": bool, "reason": str}, reporting per-category accuracy.
  • build_sft_data.sh merges two sources — xulong_* (main-text QA) and supp_* (the harder supplementary split) — and convert_to_sft_parquet.py emits a {messages, tools} parquet the trainer reads directly.

2 · Supervised Fine-Tuning

We teach the student to imitate the teacher’s tool-use trajectory. Training uses verl’s MultiTurnSFTDataset, which applies the Qwen3 chat template with the paperclip tool attached, tokenizes the whole conversation, and masks the loss to assistant turns only — the model learns to produce tool calls and final answers, never tool outputs or the user turn.

Qwen3 <think> handling. Qwen3’s template strips <think>…</think> from historical assistant turns but keeps it on the current one, so per-turn re-tokenization drifts a few tokens from a single full pass. The dataset detects this and falls back to the concatenated per-turn tokens (Token mismatch detected … Using concatenated version). This is expected, not an error.
python -m verl.trainer.sft_trainer \
    data.train_files=merged_biomedrxiv_sft_train.parquet \
    data.messages_key=messages  data.tools_key=tools \
    data.max_length=32768  data.truncation=right \
    data.pad_mode=no_padding  data.train_batch_size=8 \
    model.path=Qwen/Qwen3-14B \
    model.lora_rank=16  model.lora_alpha=32 \
    model.enable_gradient_checkpointing=True \
    engine.model_dtype=bfloat16 \
    trainer.total_epochs=1  trainer.save_freq=50
  • LoRA (r=16, α=32) over all-linear — only the adapter trains; the 14B base stays frozen, keeping checkpoints tiny and training cheap.
  • No-padding packing up to 32k tokens — agent traces are long.
  • Context length drives memory. A single 80 GB GPU does not fit 32k with offload off (the 14B base alone sits at ~56 GB, then 32k activations OOM). Either reduce to 8k context or enable FSDP offload: engine.param_offload=True optimizer_offload=True model.enable_activation_offload=True.

After training, merge_sft_checkpoint.py folds the LoRA adapter into the base weights for a standalone HF model used by RL and serving.

3 · Reinforcement Learning (GRPO)

SFT gives a student that mimics the teacher. RL makes it better by optimizing directly for correct, efficient answers — with the real paperclip tool in the loop. We use GRPO (Group Relative Policy Optimization) via verl-tool’s agentic PPO trainer.

  • Agentic rollouts: the policy emits <tool_call>…</tool_call>, a tool server executes it against the live MCP, the observation is fed back, repeat up to max_turns=8. Tool-result tokens are masked from the policy loss (mask_observations=True).
  • GRPO group: n=8 rollouts per prompt; advantages are relative to the group mean — no learned critic.
  • Tool server: verl_tool.servers.serve --tool_type http_mcp wraps paperclip; the actor POSTs actions and gets observations.
  • Policy: LoRA on the merged SFT checkpoint, FSDP with param/optimizer offload, vLLM for fast rollout generation.

Reward — reward_manager=biomedrxiv

Ground truth is a criterion like "The solution is: ~20 kcal/mol". The reward encodes the project thesis directly: be correct, be grounded in the paper, be concise.

# 1. correctness — normalized substring OR numeric proximity (15% tol)
# 2. token-efficiency bonus (only when correct):
score = accuracy*(1-w) + efficiency*w + tool_bonus
       # w=0.2,  efficiency = 1 - tokens/max_tokens
# 3. +0.1 tool-use bonus for any valid tool call

correct in  400 tok  → 0.98
correct in 4000 tok  → 0.80
wrong answer        → 0.00
bash qwen_rl/train_rl.sh --checkpoint global_step_100
# GRPO · n=8 rollouts · batch 16 · lr 1e-6 · max_turns 8 · 5 epochs

4 · Evaluation

eval_with_tools.py measures the end-to-end agent, not next-token loss: vLLM serves the checkpoint (OpenAI-compatible), each question runs the full tool loop against the same paperclip MCP, and Claude judges final answers against the criteria — reported as per-category accuracy.

vllm serve qwen_rl/checkpoints/global_step_100_merged --port 8001
python qwen_rl/eval_with_tools.py \
    --vllm-url http://localhost:8001 \
    --eval-file qwen_rl/data/_test_50.json \
    --output    qwen_rl/eval_results/step100.json

Baselines: eval_context_baseline.py answers the same questions with the relevant text pasted into the prompt and no tools (isolates “can it read?” from “can it retrieve?”); the frontier teacher’s accuracy from judge_accuracy.py is the distillation ceiling.

Results

The headline finding: a 14B open model driving paperclip over MCP matches or beats frontier models that are handed the full paper — at the lowest latency. We compare against strong baselines reading the relevant paper text pasted directly into their context (no tool calls): Gemini 2.5 Flash, Gemini 3.1 Flash-lite, Claude Sonnet 4.6, and Claude Opus 4.7. Generalizing: More Question Types & Data Sources

The MCP design makes generalization cheap. The model only ever sees one tool, paperclip(command=…), so a new question type is just a new command pattern, and a new corpus is just new content behind the same tool. The trained policy and its action space don’t change — two natural axes of growth fall out for free.

More question types — citations

Beyond fact-extraction QA, the same agent already handles citation questions — “where in this paper is reference [15] / Smith 2020 / a given DOI discussed?” — via the lookup-citation command, which finds every in-text mention of a reference (by number, author/year, or DOI) with surrounding context and block IDs:

paperclip lookup-citation "Smith 2020"   # by author / year
paperclip lookup-citation "[15]"         # by reference number
paperclip lookup-citation "10.1101/…"    # by DOI

Citation grounding is already first-class and machine-checkable. The system prompt mandates that every claim carry a structured citation — a block ID plus the exact sentence it came from (you can see these in the training answers above):

{{"block_id": "aexlhvf", "content": "a 3.5-fold increase in binding affinity after optimization"}}
# content must be a verbatim substring of block [aexlhvf]
Because a citation is structured (a block ID + a verbatim quote), it can be verified automatically: the block must exist and content must be a literal substring of it — no LLM judge needed for the grounding check. That makes “answer with correct citations” a clean, cheap reward signal — a natural next training/eval axis on top of the answer-correctness reward used today.

More data sources — arXiv (and beyond)

paperclip already spans bioRxiv, medRxiv, and PubMed Central; the same engine is extending to arXiv (the reader’s contract already lists arXiv as a supported source, and arXiv ID resolution is being hardened). Adding a corpus is a resolver/index change, not a model change:

# the same commands work unchanged over a new corpus
paperclip search "diffusion model sampler"      # now also arXiv cs.LG
paperclip lookup arxiv 2406.12345
paperclip scan content.lines "theorem" "bound"

The 14B policy trained on biomedical preprints carries over to CS / physics / math on arXiv because it learned procedure — how to find, read, and cite — not domain facts. The corpus is the knowledge; the model just drives the tool. Broaden the corpus and the same model reaches further, with no change to its interface.

Design Notes & Lessons

  • The tool is the model’s knowledge. We never fine-tune facts into weights; the model learns procedure. Update the corpus and the model is instantly current.
  • One tool, many commands. A single command-string tool (instead of dozens of typed tools) keeps the action space small and lets the policy reuse shell idioms it already knows.
  • Mask everything that isn’t the policy’s voice. SFT (assistant-only loss) and RL (mask_observations) train only on the model’s own tokens — tool outputs are context, never targets.
  • Reward conciseness, not just correctness. The token-efficiency term fights the “dump the whole paper” failure mode and matches the strict system-prompt contract.
  • Distill → RL, in that order. SFT reaches teacher-imitation; GRPO with a correctness reward and the real tool pushes past it on the hard supplementary split.
